# 小说记忆与逐章生成设计

状态：设计草案，尚未实现。日期：2026-09-08。

## 1. 本次范围与问题证据

用户决定暂不复用 my-pi-agent，先设计本项目的记忆系统。目标是支撑约 100 章小说、较长单章、跨章回忆，以及逐章交付与恢复。

用户反馈当前约三章、每章 2000 字以上就难以完成。这是使用反馈，尚未通过本次运行日志定位失败原因，不代表模型硬上限。

当前源码表明：

- runtime/agent.mjs 使用 `for (const target of task.targets) await write(target)`，正文调用已经逐章串行。
- 各章共用一次任务，完成全部起草后进行整篇审稿和修订，最后返回完整章节候选。
- runtime/writing.mjs 的 writerMessages 携带此前章节正文；规划和审稿也携带大范围作品内容。
- runtime/agent.mjs 使用字符串长度 240000 作为上下文保护；单轮任务有时间和调用数限制。
- runtime/providers.mjs 使用非流式调用，遇到 length 直接抛错；截断正文未作为可恢复片段返回。
- electron/main.mjs 会保存阶段产物，但当前生成入口没有根据这些产物恢复执行的状态机。

因此需要同时调整任务边界、输出分段和输入上下文；单纯增加摘要不能解决长单章输出截断。

## 2. 生成与交付单位

对作者：一章是独立任务和独立候选。对模型：一场景或一个场景片段是一次正文生成单位。

流程：选择章节 → 固定作品版本 → 准备记忆 → 生成场景计划 → 逐场景生成并保存 → 章节审稿 → 形成章节候选 → 采纳并提交记忆。

例如“写第 1—3 章”创建有顺序依赖的三个章节任务。第 1 章失败只阻塞其后任务；第 2 章失败不丢失第 1 章候选。

默认逐章采纳后再写下一章。若作者明确启用连续生成，可在同一候选分支内继续写：后续章依赖前面候选的准确版本，界面标明“基于未采纳章节”。放弃或改写前章时，依赖它的后章候选标记过期。候选记忆不进入正式作品。

长章节可先以每场景约 800—1500 字作为可调试验值，按剧情和模型表现调整，不作为硬性质量规则。超过预算的场景再拆片段，不要求每次生成完整长章节 JSON。

## 3. 记忆数据模型

以下是拟议字段，不代表现有代码契约。

全部记录隔离于 bookId、branchId；通过章节版本和提交标识定位有效状态。章节编号用于阅读顺序，不作为稳定主键。

| 对象 | 必要信息 | 用途 |
| --- | --- | --- |
| 章节版本 ChapterRevision | chapterId、revisionId、正文、段落标识、内容哈希 | 原文证据与改稿历史 |
| 事件 Event | eventId、参与者、地点、故事时间、行为与结果、来源 | 定位真实发生的往事 |
| 陈述 Claim | 主体、谓词、对象、有效时间、事实/信念/传闻/未知、持有者、来源 | 不把猜测和谎言当成世界事实 |
| 知情 Knowledge | 人物、陈述或事件、获知方式、故事时间、首次呈现章节 | 控制当时与现在的知情范围 |
| 故事线 Storyline | 目标、已完成变化、当前阻力、未决问题、计划里程碑 | 持续推进主线与支线 |
| 伏笔 Foreshadow | 埋设出处、可见证据、允许兑现阶段、兑现出处、状态 | 追踪承诺和回收 |
| 章节摘要 ChapterSummary | 事件引用、状态变化、故事线变化、未决问题、来源版本 | 定位材料，不替代原文 |
| 状态快照 StateSnapshot | 截至哪个提交、人物位置/物件/关系等、所依赖记录 | 避免每次重放所有章节 |
| 写作材料 ContextManifest | 选入的记忆与原文版本、筛选原因、预算、缺失项 | 可解释、可重现的上下文 |

事实的三个时间维度分别保存：故事内发生时间、读者在第几章得知、系统在哪次改稿中记录。倒叙时不能只用 chapterNumber 判断事件先后。

已采纳正文与作者明确确认的设定构成依据；未来计划单独保存。二者冲突时产生待处理问题，不让抽取模型自动覆盖正式事实。

证据引用使用 chapterId + revisionId + paragraphId/文本范围 + 内容哈希。段落被修改后旧引用仍指向旧版本，不能悄悄映射到新段落。

## 4. 写一章时怎样选择上下文

先确定目标章、场景视角、故事时间、涉及人物/物件/故事线，以及当前可使用的正式或候选分支版本。

按如下优先级装配：

1. 必需约束：本场景目标、相关世界规则、视角人物的知情边界、重要冲突限制。
2. 当前状态：涉及人物、物件和故事线的有效状态。
3. 连续性材料：上一场景结尾原文、当前章已经完成的场景摘要；局部修订时加入待改段落及邻接段落。
4. 关联证据：明确关联的历史事件原文、有关伏笔与事实来源。
5. 可选材料：相关旧章摘要、少量风格参考。

不默认携带此前全部正文，也不默认携带 100 份章节摘要。先通过故事线、实体和事件索引选候选，再用文本检索补充。语义检索是以后可以加入的辅助层。

模型窗口、最大输出与推理预算由供应商适配层管理；优先使用可用 tokenizer，没有时保守估算并记录估算方式。预算需要包含消息包装、工具定义及安全余量；不得把汉字数等同 token 数。

超预算先移除可选参考，再缩小生成/审查范围。必需证据仍放不下则拆任务或明确阻塞，禁止静默丢弃关键约束。摘要从对应原文版本生成，避免反复压缩旧摘要。

## 5. 第 58 章回忆第 12 章

假设第 12 章车站交钥匙，第 35 章揭示姐姐进入过档案室，第 58 章主角回忆交钥匙。

1. 章计划指向“车站交钥匙”事件；若没有明确 eventId，先检索消歧，不直接开始编写。
2. 取回第 12 章相关段落和必要邻接文本，以及事件的后来补充记录。
3. 分别生成“当时知道”“此刻知道”“当前可向读者揭示”的材料。
4. 写作者可以用现在的信息重新理解旧事；不得增加会改变历史因果的对白或行动并当作既有事实。
5. 若本章需要补充从未写出的往事，标为新增过去事件候选，检查它与此前行动、知情和时间线是否兼容。
6. 缺少关键出处或存在冲突时，返回具体缺口；无法定位不等于允许虚构既定事实。

示例允许：“直到现在，他才把伤口与档案室联系起来。”

示例需拦截：无依据地写成“姐姐那晚已经告诉他伤是在档案室弄的”。这改变了过去的知情状态。

秘密过滤要在检索后、交给写作者前执行；不能把完整秘密放进提示词再仅要求不要泄露。审稿可以使用更广的作者材料，但回传给写作者的修改意见同样需要过滤。

## 6. 输出截断、检查点与恢复

状态：queued → preparing → writing → reviewing → ready → accepted。

异常状态：interrupted、failed、blocked、stale、cancelled。每个状态附具体原因和可执行下一步，不将所有错误表现为重新生成。

每个生成片段保存：runId、chapterId、sceneId、segmentId、attemptId、基础版本、材料清单、模型及提示词版本、输出、结束原因、用量可用性、完成状态。

- 流式正文及时落到草稿；网络断流不等同正常完成。流式展示不会扩大模型输出上限。
- length：保存未完成片段，以最后可靠段落和剩余目标续写；半句尾部单独标记，续接时核验并保留原始尝试。
- stop：仍检查场景目标、字数和结尾完整性，不把正常结束等同文学完成。
- 超时或取消：保留检查点，只重试未完成片段，不重跑整个作品。
- 续写后检查衔接与重复；重复措辞有时是文学表达，不能简单字符串去重后就自动采纳。
- 续写有片段、章节总调用与时间预算；达到预算后留下可恢复状态，不无限追加。
- 恢复前校验输入版本和依赖；已经变化则标记 stale，不能直接拼接旧稿。
- 同一输出提交使用幂等标识；应用崩溃后重新执行不能重复追加正文。

章节审稿以当前章与相关证据为输入；跨章校对按故事线、事件和伏笔分组执行。分组审查不能保证发现全部文学问题，需要保留人工审阅。

## 7. 记忆写入与历史改稿

章节完成后抽取候选记忆，程序验证引用确实存在、实体可定位、时间字段和数据结构有效；模型检查语义冲突。程序验证来源存在不代表证明陈述为真。

作者采纳时，章节版本与记忆提交必须原子生效。正文成功而记忆未更新不能伪装成可继续生成；可暂存为待完成事务并恢复处理。

修改第 12 章时：根据依赖索引标记相关摘要、事实、状态快照以及第 58 章回忆待复核；重新抽取并比较变化，只复核受影响内容，不自动改写后续整部小说。依赖索引可能漏项，再用相关实体和故事线扫描补充检查。

初期存储建议使用本地事务数据库管理元数据、提交和依赖，正文版本采用不可变内容记录。具体数据库驱动、桌面打包和迁移方案在实施前验证；此文未增加依赖。

## 8. 页面行为

- 单章入口：“生成本章”“继续未完成章节”“重试失败场景”“查看生成依据”。
- 进度展示：“第 2 章，第 3/5 场景”，可查看已经保存的草稿。
- 每章独立显示待生成、生成中、待审稿、待采纳、已采纳、失败、依赖过期。
- 连续生成显示队列及依赖，单章失败后暂停后续，不覆盖已完成章节。
- 记忆页优先支持来源跳转、冲突和缺失信息查看；复杂知识图谱可后置。

## 9. 分步落地与验收

第一步：先修交付单位。单章独立任务、场景分段、持久检查点、失败恢复；去掉生成与交付必须等待整批成功的耦合。

第二步：增加最小记忆。章节摘要、事件、人物状态、知情和原文出处；接入按需材料装配与预算。

第三步：补故事线与伏笔追踪、回忆消歧、秘密过滤、改稿依赖失效和连续候选分支。

第一步仍需要有限的材料装配以防输入爆炸；未完成第二步前不能宣称支持 100 章稳定连续性。

验收场景：

| 场景 | 通过条件 |
| --- | --- |
| 单章 6000 字 | 按场景完成，保存可见；实测字数达标并通过衔接检查，不要求一次输出全部 |
| 三章队列在第二章失败 | 第一章产物可使用，重启后只恢复未完成步骤 |
| 第 58 章回忆第 12 章 | 能定位正确事件和原文，区分当时与现在的知情 |
| 两个雨夜、两把钥匙 | 不因词语相似混合事件；无法消歧时明确指出 |
| 回忆缺少伤口来源 | 标为未知，不当作既有事实补写 |
| 第 12 章改稿 | 第 58 章相关依赖失效并提示复核，其他不相关内容不重生成 |
| 人物说谎或猜测 | 保留陈述者和性质，不自动提升为世界事实 |
| 倒叙与秘密 | 正确使用故事时间与揭示顺序，写作者材料无越界秘密 |
| 断流、length、正常早停 | 各自进入正确处理分支，不重复拼接或误标完成 |
| 100 章已有语料 | 输入材料不随全文线性膨胀，关键证据召回可验证 |

先用固定小样本验证协议与恢复，再用已有长篇测试材料验证检索和预算，最后评估持续生成的文学质量。三者分别报告，不能用“可导入 100 章”代替“能稳定写出 100 章”。
