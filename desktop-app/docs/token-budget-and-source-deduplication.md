# Token 预算与原文去重

## 问题与处理

旧预算把每个 ASCII 字符算作 1 Token、其他字符算作 2 Token。第五章已有 GLM 日志里，本地估算约为实际输入的 2.61—2.64 倍。JSON 已是紧凑格式；换成 YAML 没有改善本项目样本的 Token 开销。

0.1.42 保留 JSON、现有作品结构与场景纯文本输出，调整请求预算和重复材料：

- `model-budget.mjs` 使用固定版本 `gpt-tokenizer@4.0.0` 的 `o200k_base` 本地 BPE。每次请求加 512、每条消息加 64 的协议余量，再乘至少 1.25 的安全系数。计数针对 `messages[].content`，不重复计算 HTTP JSON 转义；特殊标记按普通文字计数。
- 这是代理估算，不是 GLM/MiniMax 官方分词器。应用上限仍为 60,000，最终输入加本次输出预留统一核算。没有扩大供应商窗口、修改输出上限或新增 Tokenizer API 调用。
- 同一任务中，以供应商返回的 `usage.prompt_tokens / 本地基础估算` 校准。安全系数只会上调，至少覆盖已观察比例再加 15% 余量；缺失、零值、非整数及仅有 `total_tokens` 的响应不参与。小样本不能保证新内容一定不会低估，日志同时显示估算和实际值，真正超出应用预算仍拒绝。
- 校准快照保存在章节检查点的可选 `tokenBudget` 字段中，按请求的供应商、模型、接口及估算器版本隔离。供应商可能把模型别名路由到新版本，日志另行记录响应模型；系数只增不减。旧任务没有此字段时自动采用默认值。作品、原文与引用结构不迁移；新任务重新开始校准。旧讨论/写作入口也统一使用相同估算与纠错预算，但只在当前运行内保留校准。
- 写作记忆软额度换算为 10,000 BPE 估算 Token，防止预算校准后反而灌入更多历史。最近章、明确引用、本章正文与草稿仍完整保留；其余记录按场景相关性选择。审稿保留完整原有证据，不使用写作检索结果代替证据。
- 记忆抽取删除重复 `source`，仅发送 `sources: [{sourceId,text}]`。编号原文拼接后等于原片段，校验仍用完整原片段，保存的 `sourceText` 与逐字引文不变。
- 实测发现原提示遗漏了校验器的 16 条记录上限。本版从共享常量写入数量与摘要长度限制，并明确 kind 与 epistemic 的不同取值，避免返回 23 条记录或把 belief 填入 kind 后无效重试。
- 结构化重试保留原任务及证据。小于等于 3,000 估算 Token 且不会挤满请求的失败响应完整附回；否则仅发送最多 1,600 字符的错误说明，请模型重新生成。不会截断 JSON 后冒充完整响应。章节原始失败输出仍完整保存在 `fragments`；每阶段仍最多两次尝试。

## 验证方式

- `npm test`：预算、原文逐字保留、编号校验、纠错、生成中断与恢复、审稿修订、版本等回归。
- `node scripts/verify-token-budget.mjs`：用既有第五章检查点组装写作、审稿、记忆请求，对比旧预算和请求体；不会调用模型或修改正式作品。
- `node scripts/verify-token-budget.mjs --live`：额外通过现有 GLM Coding Plan 实测首个记忆片段，最多两次生成，验证编号及原文引用。输出在 `verification/token-budget-v2/`。
- 打包后用既有 `scripts/verify-repair-plan.cjs` 在独立目录重放真实 GLM 响应，核对一次恢复到候选、重启、采纳和完整版本。重放验证桌面链路，不代替新模型生成质量验证。

版本、实际计数、桌面核验与验证边界见 `verification/token-budget-v2/验证报告.md`。

## 审稿输出截断恢复（0.1.47）

第六章日志的输入估算 29,469 在应用预算内，失败来自固定 6,500 的输出额度。旧实现直接抛错，没有保存该次截断正文和 usage；恢复又按 6,500 请求，因而不能靠输入去重解决。本轮真实接口请求 glm-5.2 时响应标记 glm-5.3，并返回思考用量，诊断同时记录两者。

- 章节工作流中的结构化调用接收 `length` 响应，先保存原始返回文本和 `responseMeta`（结束原因、实际模型、usage、输出预算）。即使内容恰好是完整 JSON，也不解析或采纳为成功；只有思考用量、没有正文的截断同样保留诊断。
- 输出截断后完整重新生成，不续拼半截 JSON。自动输出额度最多翻倍两次，上限 24,000，仍受输入估算加输出预留不超过 60,000 约束。通常审稿为 6,500 → 13,000 → 24,000；上下文余量不足时增长更少或明确停止。
- 格式/证据错误最多纠正一次，与两次扩容合计最多四次请求。再次恢复属于用户新发起的一轮；沿用已提高的额度，不无限自动调用。正常成功请求仍使用原额度。
- 可选检查点字段 `outputBudgets` 按供应商、请求模型、入口和原始消息内容的摘要保存额度，恢复编号变化不影响。同一键的原始响应不再覆盖；旧检查点无需迁移。
- 审稿消息把句子投影为 `[句子编号, 原文]`，直接使用明确编号。原文、文档版本和持久化引用地址不变。越界错误说明真实段数/句数，继续严格拒绝无效证据。修订与复核消息保持既有结构。
- 实测额外发现修订依据把原文归错来源、将中文引号改成英文引号。依据校验现在一次收集多条错误，并给出原文候选辅助唯一一次纠错。候选搜索忽略标点与空白只用于错误提示，实际接受条件仍是指定来源内逐字唯一匹配，不自动改引文或挪动来源。
- 仅保留 JSON，未切换 YAML、供应商、套餐入口或思考参数。其他旧入口的供应商调用仍默认拒绝截断。

新增验证：`tests/structured-output.test.mjs`、审稿恢复编号回归、显式句号逐字回填回归。`scripts/verify-review-output.mjs --live` 使用隔离第六章快照重新进入当前轮审稿，保留草稿、既有补丁和作者裁定，最多十次真实请求，结果不写正式作品。打包后的 `scripts/verify-review-output-desktop.cjs` 注入一次截断并重放本轮真实响应，验证自动扩容和重启。详细证据在 `verification/review-output-fix/`。
