# 审稿与恢复的状态契约

## 必需 workflow skill 与字段归属（2026-09-09）

`runtime/skills/novel-workflow/SKILL.md` 是小说 Agent 的运行时资源，在规划、正文、记忆、审稿、裁定、依据核对、补丁和复核请求中加载。`runtime/workflow-skill.mjs` 启动时读取并校验资源，缺失即失败；打包必须包含该文件。它不是给 Codex 开发流程使用的个人技能。

技能文本说明模型应遵守的流程，强制边界由代码执行。每个结构化调用必须由程序登记阶段及 Zod 契约，缺少或伪造契约、审稿阶段不匹配，在请求前拒绝；补丁要求已有修订依据，复核要求已有保存的补丁。其余步骤依赖继续由既有规划 DAG 和章节流程控制，没有另建一套独立状态机。

| 数据                                                    | 谁决定                   | 接收边界                                                                   |
| ------------------------------------------------------- | ------------------------ | -------------------------------------------------------------------------- |
| 字段名、层级、类型、枚举、数量上限                      | 程序 schema              | 字段表从同一 schema 生成；模型响应逐层拒绝未声明字段，不再静默剥掉多余字段 |
| 正文、解释、建议、人物声音                              | 模型生成                 | 类型、篇幅和业务规则校验；不能因此保证所有语义判断正确                     |
| `sourceId`、段句编号、已有问题与章节 ID                 | 模型从本批输入选择       | 检查真实来源、位置、引文、允许修改范围；不是任意创建 ID                    |
| 创建人物、关系等新实体 ID                               | 允许创建的阶段由模型给出 | 格式、唯一性、引用关系由作品 schema 校验                                   |
| 本批提供范围、来源哈希、稳定问题 ID、补丁 `baseVersion` | 程序计算或绑定           | 不再要求模型抄写；旧补丁若主动携带不同版本仍拒绝，不能用新版本覆盖过期补丁 |
| 阶段、成功状态、纠错预算、作者回答、正式作品采纳        | 程序及作者操作           | 模型无权返回这些字段来改变状态；独立复核通过才提交草稿补丁，候选仍等待采纳 |

新补丁输出只要求 `replacements`，版本绑定到本次请求的原文。旧专项 `issues + continuityChecks`、旧记忆逐字 `quote` 和旧补丁相同版本号是显式声明的兼容格式；不是允许模型自创扩展字段。旧已校验检查点沿原业务契约恢复，新收到的响应先校验 wire 契约，再定位原文和核对业务规则。

结构化节点保存技能版本、内容哈希和阶段 ID；技能哈希进入恢复协议与输入身份。技能及字段表在分批前计入输入预算，同一请求只注入一次。正文请求也加载同一技能，但输出仍是正文而非 JSON。当前供应商接口没有启用服务端 `json_schema` 受限生成；模型仍可能输出非法 JSON，程序负责拒绝、保存诊断和有界纠错，不能把技能文档视作模型绝不会犯错的保证。

验证：`tests/workflow-skill.test.mjs` 覆盖缺少契约零调用、未知嵌套字段、模型伪造采纳字段、跳过依据/补丁、过期版本，以及一次作者确认后补丁、复核字段失败、断网、序列化恢复和复审的完整链路。`scripts/verify-workflow-skill.mjs --live` 使用保留的第三章原文和原 MiniMax 审稿发现验证一个问题组，在补丁后注入断网再恢复；记录真实请求和结果，不代作者作答，不写正式作品，也不代表整章通过。报告存于 `verification/workflow-skill/`。

## 同一输入的持久化纠错与专项单一问题来源（2026-09-09）

第三章截图中的 JSON position 1378 错误来自数字字段后多出的引号，响应以 `stop` 结束，并非额度截断。旧流程每次恢复都重置纠错次数，失败请求的诊断没有作为下一请求的执行计划保存，因此同一批次可以一直重新调用模型。另外，模型同时维护 `issues` 和 `continuityChecks` 两份发现，经常相互矛盾；要求抄全 `searchedSources` 也把漏抄名单误当作审稿失败。

- `structured-step.mjs` 使用协议版本、模型配置、逻辑步骤和原始输入的指纹标识节点。恢复编号不参与身份。节点保存原始输入、原始响应、诊断、下一次纠错依据、已用纠错次数及输出扩容次数。
- 状态为 `pending → requesting → received → succeeded/correcting/exhausted`。收到响应后先落盘；校验前退出，恢复直接校验该响应。断网或取消后沿用已保存的纠错计划；纠错期间截断也不丢之前的诊断。已成功节点直接复用校验过的结果。
- 审稿和依据核对最多两次纠错，其他结构化步骤一次；最多两次输出扩容。次数跨重启保存，不能通过恢复编号刷新。`length` 始终不能提交结果。预算耗尽保存 `STRUCTURED_RECOVERY_EXHAUSTED`，状态投影停止显示恢复按钮，Checkpoint 入口也拒绝原样恢复；不会转成作者情节确认。只有真实输入或协议变化才建立新节点。
- 新专项结果只在 `dimensions` 的每个维度内填写问题；问题编号和汇总结论由程序生成，并在分批及综合审稿合并后重映射关联。新旧两种结果结构不得混用。旧响应仍按原证据规则校验，`problem` 却没有问题条目仍然拒绝。
- 程序记录本批实际提供的来源哈希和原始段号，不再要求模型抄 `searchedSources`。该记录只证明提供了材料，不证明模型逐项检查，更不证明全书没有某事件。引用定位、不同证据要求、当前章修改边界和独立复核保持不变。

旧任务没有持久化节点时，为未完成请求建立一次新协议预算；已保存草稿、作者裁定、已完成审稿阶段和补丁提交保持可恢复。协议改变后的单批结果缓存按新提示词区分。`STRUCTURED_RECOVERY_VERSION` 是执行契约版本，校验语义改变且需要重新处理耗尽节点时必须更新版本；不能为了恢复点击而清空记录。回滚到旧应用会失去此项预算约束，因此回滚前保留完整任务备份。

验证：`tests/structured-step.test.mjs` 覆盖持久化状态转换和零调用重复恢复；`tests/review-result.test.mjs` 覆盖单一发现结构、引用拦截、范围记录和问题合并。`scripts/verify-review-protocol.mjs` 使用第三章故障快照对照旧校验，并重放截图的真实坏响应；`--live` 只验证原供应商的一批专项审稿及结果缓存，不代表整章已修订或采纳。报告存于 `verification/review-protocol/`。

## 作者裁定重复询问与补写锚点（2026-09-09）

真实第二章已保存八次相同的毛毯细节取舍，正文始终未变化。旧流程把作者选择保留的原文重新交给核对员要求确认；另一个问题需要在正确原句旁补写，但程序将所有锚点都当作必须删除的错误片段，补写完成后仍判失败。最后两项发现被模型改判为 `dismiss`，循环才退出。候选完成和采纳是独立请求，没有按确认次数自动采纳的规则。

- 作者选择 `preserve_evidence` 的当前断言，若是同一项缺少前情或无依据推断，且保留事实仍能逐字定位，程序按该取舍结案。稳定编号只辅助关联，不按段号放行其他发现；新断言、不同事实、真实矛盾、过期引用和选择历史证据仍须正常核对。
- 复审将原来的整段目标缩为作者选定的完整一句时，仍识别为相同保留事实，即使引用了不同证据或旧记录没有问题类型。只接受精确事实文本，不按关键词或局部片段扩大授权；旧版已重新打开的同一发现也恢复为结案。
- 作者回答保留结构化动作和原文事实，缓存只恢复当前问题集合，不复活已经驳回的问题。已裁定的问题再次返回 `needs_confirmation` 属于模型执行错误，进入有次数限制的纠错，不再次要求用户表达同一取舍。
- 旧版未回答的问题全部与已有裁定匹配、正文版本和来源哈希不变时，可直接恢复，复用已存答案，不伪造作者消息或增加裁定数量。含新问题、部分作答或来源过期时仍保持待答流程。
- 修订目标增加 `operation`：`replace` 必须消除错误片段；`insert_before` / `insert_after` 以原文为插入位置，保留完整原段，在指定位置补入实际内容。仍检查范围、原文哈希、全部目标覆盖和独立复核。旧已提交补丁默认 `replace` 恢复；旧未提交方案重新核定。

`tests/author-decision-loop.test.mjs` 覆盖一次确认、序列化恢复、补写、独立复核与再次审稿，以及新问题不能误用旧裁定等边界。`scripts/verify-author-decision-loop.mjs` 在当时循环状态的任务副本恢复到正文与记忆候选，默认按问题组重放最终原始响应，`--live` 使用原供应商。结果保存在 `verification/author-decision-loop/`；测试不修改正式已采纳正文，也不执行采纳。

## 修订依据与待作者确认恢复（2026-09-09）

第二章真实任务的依据核对返回 `needs_confirmation` 与 `targets: []`，表示事实尚未确定，暂不修改正文。旧校验把它与 `repair` 一同要求必须有修改片段，导致重试始终失败。另一次中断来自证据抄写把“顿了一下”改成“顿一下”。

- 三种决策分别校验：`repair` 必须有逐字定位的修改片段；`dismiss` 不得带修改目标；`needs_confirmation` 可以没有修改目标，保留同一正文版本中已校验的问题位置，仅用于作者问答。过期、缺失或历史正文位置不能作为此项回退依据。
- 新修订核对请求的 `evidence` 使用明确的原始段句编号，由程序回填原文；旧检查点的 `sourceId + quote` 继续严格校验。若同时提供编号和引文，两者必须一致。`targets` 仍要求逐字片段和最小修订要求，不按相似度自动纠正。
- 引用、缺目标及决策冲突同时反馈，修订依据核对最多自动纠错两次。专项审稿中已有问题但其他证据校验失败时，不再误报为遗漏问题；真实遗漏仍拦截。
- 待作者作答时不生成补丁；作答后携带作者约束重新核定范围。未回答的任务在重启后保持同一问题，不重新审稿或丢弃草稿。

`tests/repair-anchor-recovery.test.mjs` 覆盖上述契约和失败恢复、重启、作答后继续；`scripts/verify-repair-anchor-recovery.mjs` 在隔离的作品与任务快照上重放原始响应，`--live` 使用任务原供应商，仅验证到作者等待或补丁入口。修复前后对照和 MiniMax-M3 两次请求实测均保存在 `verification/repair-anchor-recovery/`，正式作品和任务不由验证脚本修改。该验证不代表整章已经完成修订或采纳。

## 结构化结果与时间索引恢复（2026-09-09）

MiniMax 实际响应曾在闭合 JSON 后追加 `target` 等字段，把 `timeAnchors` 的数组下标误作第 0 段，并在同一响应中遗漏问题条目、超出证据数量限制。解析或证据失败不能通过丢弃尾部字段、补造地址或静默删除问题来放行。

- 审稿用的时间/事实索引按本批正文逐字定位 `references`，仅忽略引文边缘的空白分隔符。命中的引文不再重复发送；未命中的引文继续保留为待回查线索，不能直接充当正文地址。
- 分批保留原始段句编号。越界提示说明本批可用来源或编号；引用范围、专项证据数量和问题/结论一致性合并反馈，减少逐个错误消耗恢复次数。
- JSON 语法错误要求从头返回完整对象，不把坏响应作为格式范本；原始响应仍完整存盘。审稿和修订依据核对最多自动纠错两次，其他结构化任务保持一次；包括最多两次输出扩容，单批最多五次请求。
- 当时重试耗尽仍保存为可恢复失败；后续“持久化纠错”修复已改为预算跨恢复保存，耗尽后停止原样恢复。不缓存无效审稿结果，保留场景和作者裁定。

## 范围与验收

保留分场景生成、正文引用校验、最小补丁、独立复核和作品采纳边界。本次统一审稿到恢复的控制流程，不迁移生成引擎。

- 审稿、裁定、作者等待、补丁、复核分别存档；恢复继续未完成阶段。
- 技术失败可重试，只有事实无法裁定才向作者提问。
- 问题拥有跨轮编号、证据快照、状态和重开原因；不得用重复审稿覆盖处理记录。
- 作者回答形成不可变约束，后续裁定、补丁、复核和最终审稿都收到约束；旧地址不能冒充当前原文。
- 同一回答重发幂等，半答、答完后中断和旧版检查点可以恢复。
- 草稿和补丁提交在同一检查点写入；未通过复核不能改变草稿。
- 对话展示同一任务视图，技术重试不伪装成情节问题。

## 现状与边界

`chapter-agent` 负责生成及结构化调用；`paragraph-review` 负责引用、补丁校验和审稿循环；`review-resolution` 负责裁定及回答；`checkpoint` 保存任务；Electron IPC 保存对话并投影任务；`useReviewChat` 组织问答；`StudioContext` 拥有请求副作用。现有缓存只能重放调用，不能准确说明流程停在哪一步。

新增独立的审稿状态模块，统一阶段、问题记录、作者约束与错误分类。原检查点保留，增加带版本的审稿状态和当前轮快照；旧提交仍按原文版本逐笔验证。任务视图从检查点推导，前端不持有第二份业务状态。

## 状态与恢复

审稿 → 裁定 → 必要时等待作者 → 补丁 → 独立复核 → 提交 → 下一轮审稿 → 完成。

网络中断 → 保存阶段与执行计划 → 可恢复；模型/协议失败 → 保存诊断 → 在同一节点预算内纠错，耗尽停止。恢复跳过已保存的成功阶段，不把失败缓存当成功，也不刷新纠错预算。补丁失败保留原稿，复核失败保留待复核补丁。反复未通过复核或轮次预算用完属于执行未收敛，不要求作者再次表达相同选择。

## 兼容与回滚

旧任务保留场景、提交记录和作者回答，首次恢复时导入新状态。新状态是附加字段，不删除旧缓存。上线前保存打包版本和验证报告；回滚前备份任务文件，避免旧版忽略新状态后重跑阶段。正式用户作品不用于破坏性测试。

## 决策记录

不把整个写作引擎替换为通用 DAG；这里需要先明确节点输入、提交点、重试语义与作者约束，再考虑调度器抽象。模型负责提供发现和证据，状态转换由程序控制。

## 实现落点

- `runtime/review-workflow.mjs`：持久阶段、稳定问题编号、证据历史、作者约束、失败分类和任务投影。
- `runtime/paragraph-review.mjs`：每轮保存审稿结果、决策、补丁与重试次数；恢复跳过已完成阶段，原文和提交链继续按哈希验证。最终审稿和补丁复核必须逐项回填作者约束的检查结果。
- `runtime/review-resolution.mjs`：只将未裁定的事实放进问答；自动决定与作者决定合并进入修订。技术错误交给恢复流程，不生成虚假的作者问题。
- `runtime/checkpoint.mjs`：恢复失败节点；兼容旧版待答和已答未修订任务；同一答复重复提交不再启动执行。
- `electron/main.mjs`：统一投影任务；可恢复的审稿故障作为对话消息保存；回答重发允许旧 revision，但只确认收讫，不执行新写作。
- `src/features/ReviewProgress.tsx`：纯展示审稿状态；`useChapterTask` 防止切换作品时短暂显示上一作品任务。

问题关联采用当前证据文本与目标位置的保守匹配：无法唯一关联时创建新问题，不用模型的临时序号猜身份。作者约束保留裁定时的事实快照；当前正文找不到唯一逐字匹配时明确返回空地址，不沿用旧段落编号。这些约束在当前任务内持续生效，跨章节的作品记忆仍沿用原有机制。

## 原文定位与范围纠错（2026-09-08）
