# Novel Agent Studio Desktop

本地桌面原型：Electron + React/TypeScript + React Flow。GLM / MiniMax 真实接口接入；作品保存在本机。当前是可操作原型，不是已经通过文学质量评测的完整小说 Agent。

当前支持按模型设置Token预算、分批审稿、按问题局部修订，以及随应用提供的本地Embedding与SQLite混合检索。记忆按本章原文增量更新，向量命中与结构化记录合并召回，相同原文仅在节省Token时复用。流程与验证入口见[模型预算与本地混合检索](docs/model-budget-and-local-retrieval.md)和[分层记忆与增量更新](docs/layered-memory-and-incremental-updates.md)。

## 启动

在此目录执行：

```sh
npm ci
npm run prepare:embedding
npm run desktop
```

- `npm run dev`：浏览器交互预览，地址 `http://127.0.0.1:5178/`。该模式只用固定演示数据，不调用模型、不读取密钥。
- `npm test`：运行领域与接口测试。
- `npm run pack`：生成 Apple Silicon macOS 应用，位于 `release/NovelAgentStudio-darwin-arm64/NovelAgentStudio.app`。
- 修改源代码后执行 `npm run desktop` 重新构建；仅 `npm start` 使用上一次构建。

每次 `npm run build`（包括 `desktop` 和 `pack`）或启动 `npm run dev`，自动递增应用 patch 版本，并生成 `build-info.json`。完整版本格式为 `基础版本+北京时间到毫秒.源码指纹`，左下角和桌面“关于小说工作室”可查看。源码指纹覆盖前端、运行时、桌面入口、构建脚本及依赖清单，不读取密钥或作品数据。基础版本同步写入 package.json、package-lock.json 和 macOS 包信息。失败的构建也会消耗一个版本号；`npm start` 不递增版本。打包后须退出旧应用再打开新包，已运行的旧进程不会自动变成新版。

## 操作路径

1. 在“作品管理”新建作品，或通过左上角作品下拉框切换。每部作品的作者、设定、人物、章节、对话和候选独立保存；支持重命名、归档与恢复。至少保留一部未归档作品。
2. 在“作者与作品”选择作者预设，填写人格、文学积累、口癖、引用偏好、故事前提、预计章节和字数，点击保存。
3. 在“模型连接”选择 GLM 或 MiniMax。现有配置只读取下述已授权 `.env`；界面只显示是否有密钥，不回显内容。
4. 在“创作对话”请求生成大纲、人物、关系与章纲。查看完整候选后采纳，或放弃后重新讨论。
5. 在“人物关系”拖动节点保存布局；坐标重叠时点击“自动排列”。从一个节点右侧圆点连到另一个节点左侧圆点建立关系。点击人物编辑档案，点击连线编辑方向、关系名和说明。浏览器拖动持久化已验证；原生自动化拖动尚需人工复验，详见验证记录。
6. 规划具备总纲、真相、双时间线、伏笔、人物关系、章纲后，在对话中请求某一章正文。正文候选经采纳后出现在“章节阅读”。
7. 阅读页支持章节切换、总纲查看和字号调整；正文修改通过创作对话提出，例如“将整篇扩写到8000字，保留3章”。查看修订范围和完整候选后采纳；普通保存仍不允许直接改正文，修订不能删除章节。

8. 左侧“下载作品备份”导出完整作品 JSON；“下载作品正文 (.md)”按章号导出已采纳正文，包含书名与章节标题，不包含梗概、真相、对话或候选。没有正文时禁用正文下载。

未保存的表单草稿留在当前页，切页或切换作品前请保存。切换作品会清空页面草稿、人物选择和阅读状态。生成期间不能切换、新建、重命名或归档作品；停止任务并等待结束后可继续管理。若生成期间作品发生变化，候选不会覆盖新版本；请基于最新状态重试。处理上一份候选后再开始下一轮生成。

## 模型配置与密钥

首次使用先在项目根目录将 `.env.example` 复制为 `.env`，填写 `ZAI_CODING_CN_API_KEY`、`MAIN_MODEL` 和 `MINIMAX_API_KEY`；只用一个供应商时可留空另一个密钥。已有 `.env` 时直接编辑，避免覆盖。本地 `.env` 已被 Git 忽略，示例文件不含密钥。

桌面端优先读取本机已保存的加密配置；缺少某个供应商密钥时，才从以下位置导入该供应商配置：启动环境变量 `NOVEL_AGENT_ENV` 指定的文件优先；未指定时，开发版读取项目根目录 `.env`，安装版读取 `~/Library/Application Support/novel-agent-studio/.env`（设置 `NOVEL_AGENT_DATA_DIR` 时改用该目录）。不再自动读取其他项目的配置。安装版也可直接在“模型连接”手动填写密钥。

命令行评测脚本默认读取项目根目录 `.env`，不受执行时工作目录影响，也支持 `NOVEL_AGENT_ENV`。该变量是启动进程的环境变量，不是写入 `.env` 的配置项，例如在 `desktop-app` 目录执行 `NOVEL_AGENT_ENV=/绝对路径/模型.env npm start`。只读取上述三个字段，不将密钥注入前端或打包产物。导入成功后由系统安全存储加密，只将密文写入本机配置；源文件读取超过3秒时返回未配置状态，可手动输入。修改 `.env` 不会覆盖桌面端已有的加密密钥，要更新已配置密钥请使用“模型连接”。

- GLM：`https://open.bigmodel.cn/api/coding/paas/v4`，模型沿用 `MAIN_MODEL` 的 GLM 值。
- MiniMax：默认 `https://api.minimaxi.com/v1`、`MiniMax-M3`，支持在设置中改为官方 `api.minimax.cn` / `api.minimax.io` 的 `/v1` 入口。
- 不自动切换供应商或按量计费端点。MiniMax Key 所属资源由服务端决定；客户端连通测试不证明具体扣减了哪类额度。
- 手动更新密钥时使用 Electron safeStorage 加密，密文保存到应用数据目录；系统安全存储不可用时拒绝明文保存。
- GLM Coding Plan 官方限定指定工具/产品环境；独立写作应用的套餐适用性未因接口连通得到确认。

按2026-09-08核对的资料实现：[GLM Coding Plan](https://docs.bigmodel.cn/cn/coding-plan/quick-start)、[MiniMax OpenAI兼容接口](https://platform.minimaxi.com/docs/api-reference/text-openai-api)、[MiniMax Token Plan](https://platform.minimaxi.com/docs/token-plan/quickstart)。两种兼容接口均由主进程调用，不采用会员网页登录或私有接口。

## 存储与恢复

应用数据目录：`~/Library/Application Support/novel-agent-studio/`。

- `library.json`：作品索引、归档状态和上次打开的作品 ID。
- `projects/<作品ID>/project.json`：该作品的设定、关系坐标、章节、对话和候选状态。下列备份、历史版本与运行记录也位于该作品目录。
- 原单作品 `project.json` 首次启动自动迁入作品库，保持版本号和内容不变；原文件及根目录历史记录保留，后续不再写入旧文件。迁移时先落作品，再提交索引。
- `project.json.bak`：上次成功保存的作品版本。
- 根目录 `providers.json`：所有作品共享的模型设置与导入/手动输入密钥的密文，没有明文密钥。
- `runs/`：运行状态、模型标识、使用量（可用时）及错误分类；不记录密钥。
- `last-run.json`：最近一次成功生成摘要。
- `runs/<runId>/`：正文任务的原始模型输出、场景规划、稿件、审稿和字数校验；失败/取消不自动采纳，阶段文件用于诊断，尚不支持自动续跑。
- `versions/revision-<版本号>.json`：采纳正文修订前的完整原稿快照，独立于滚动 `.bak`；若存档失败，拒绝覆盖原稿。可退出应用后手动从此文件恢复。

写入先通过结构校验，再以临时文件重命名替换；保存操作在主进程串行执行，使用版本号防止迟到结果覆盖。文件损坏不会自动重置为新作品。可退出应用后，从 `.bak` 或“导出作品备份”生成的 JSON 恢复到对应的 `projects/<作品ID>/project.json`。恢复前保留当前文件；尚无备份导入界面。

已采纳产物在重启后恢复；运行中的模型调用不支持进程重启续传。强制退出时可能没有最终运行日志，不能将其解释为成功。

## 实现边界

以下旧正文流程限制属于 `runtime/agent.mjs`；当前具备规划的正文任务使用文末“逐章生成与故事记忆”描述的新流程。

- 支持本地多作品隔离和管理，模型连接配置在应用内共享；这里的多租户边界是作品空间，尚无多用户登录、账号权限或云端租户隔离。尚未实现正式历史版本面板或分支管理。
- 正文流程：识别本次请求的修改范围与目标 → 场景与连续性规划 → 因果/动机审查及一次计划修订 → 分章起草 → 按段落编号定位的整篇证据审稿 → 事实与知情专项复核 → 最多两轮修订与复查 → 字数/范围检查 → 人工采纳。保留上一轮请求作为历史，当前请求优先；模型自行声明的完成字数不作为证据。
- 事实专项使用独立的逻辑校对提示，不继承写作者的风格要求。默认关闭思考；GLM/M3开启思考的实验均出现过输出预算耗尽，暂不作为默认配置。GLM参数依据 [官方思考参数](https://docs.bigmodel.cn/cn/guide/capabilities/thinking)。
- `novel-studio-3-horror`：本次用户请求直接传入写作与审稿，恐怖规划在既有场景字段中说明人物依靠、合理应对、反常后果及选择变化。明确要求宇宙恐怖时检查现实认知是否受到动摇，不以海雾、古籍、身份反转或恐怖词汇数量代替效果。普通题材不强制宇宙恐怖。
- 题材承诺缺失可用 `horror` 审稿类别进入原有修订闭环；严重问题必须有目标依据、具体段落及阅读后果，普通烈度偏好仍是建议。连续性专项增加日期方向、事后证词、设备处理过程与物件归属检查。上述语义判断依赖模型，不是确定性的文学质量保证。
- MiniMax-M3 默认关闭思考。实测开启思考的规划任务曾耗尽输出预算，因此不将其默认开启；评测脚本可用 `NOVEL_AGENT_REASONING=1` 显式实验 `thinking: adaptive`，依据 [官方兼容接口文档](https://platform.minimaxi.com/docs/api-reference/text-openai-api)。思考与正文分离，仅保存正文和用量，不保存隐藏思考文本。
- JSON 解析先严格解析；对确已闭合但漏转义的引号，可借助 `jsonrepair` 只添加反斜杠，之后重新验证。拒绝补齐截断输出、括号、字段或正文，不能把残缺输出修成成功。
- 创作、草稿修订与分批审稿不设本地总时长上限，作者可随时点击停止。旧版正文入口最多26次调用，最多6个目标章节、每章6000字、目标合计18000字。每个结构化阶段至多重试一次。取消立即传递到接口；取消、字数不足、未解决的严重审稿问题不会返回可采纳的正文候选。模型连接测试的60秒等待上限只用于测试连接，不影响创作。
- 字数口径：汉字逐字计，连续英文或数字串计一字，不计标点空白。在“作者与作品”配置每章字数容差，支持固定字数或目标字数百分比（正文最低100字）。默认±500字，目标4500字时4000—5000字含边界均达标；例如目标10000字、±20%时允许8000—12000字。设置按作品保存，模型候选不能覆盖。保存后对新任务生效；恢复已有任务沿用启动时的容差，旧任务仍按原默认值恢复。结果显示目标、允许范围与实测值，整篇范围按目标章节的容差累加。单章目标覆盖默认值，整篇目标扣除保留章节后在目标章节之间分配。
- 未准备好规划时仍先提出规划供采纳，不在同轮直接生成全文；该路径最多2次调用。规划目前主要依赖提示与结构约束，尚未接入与正文同等的独立审稿。
- 原型使用独立供应商适配层，没有直接引用或修改 my-pi-agent 核心，也没有导入其全局工具和记忆。
- 人格与文风档案已经参与提示词；减少AI味、语义连续性、长篇质量仍需按上级评测协议验证。结构合法不能代表文学质量合格。
- 总纲、双时间线与伏笔暂以文本保存；没有完整 Fact/Knowledge 图谱或自动引用核验。规划/审稿可见作者真相，写作者不直接接收真相和人物秘密字段，只接收当前章场景计划、允许事实、前文及目标原稿。规划或审稿仍可能间接泄密，不能声称已实现严格语义隔离。
- 对话展示阶段进度，最终候选完成后展示；未实现逐字流式正文。
- 打包产物为本地 macOS arm64 应用，未做签名、公证或 Windows/Linux 验证。

Electron 使用 contextIsolation、sandbox、关闭 nodeIntegration，并将 IPC 限定到当前主窗口；参考[官方安全说明](https://www.electronjs.org/docs/latest/tutorial/security)。

## 可复现的真实调用验证

在此目录运行（读取授权配置，不改动输入作品、不自动采纳）：

```sh
node scripts/evaluate-writing.mjs 输入作品.json verification/独立结果目录 minimax "将整篇扩写修订到8000字，保持3章"
```

可显式选择 `glm`；不会自动切换供应商。输出包括输入快照、阶段原始输出、场景规划、修订稿、审稿、真实计数和失败信息。成功时另写 `candidate.md` 和 `result.json`。单次模型审稿通过只说明流程完成；文学效果仍按上级评测协议做人工比较，不能代表稳定达到某位作者或模型的水平。

开发调试可设置 `NOVEL_AGENT_REPLAY_DIR=以前的结果目录`，仅复用同一作品快照、请求、模型下的任务解释、场景计划和最新已保存稿件；审稿和后续修订仍真实调用。报告分别写入 `replayCalls` 与 `liveCalls`。重放不是全新生成，也不是独立文学评测样本。

只验证审稿能力、不生成或采纳正文，可运行：

```sh
node scripts/evaluate-review.mjs 输入作品.json verification/新的审稿目录 minimax
```

该脚本分别调用综合审稿与事实专项，保存原始请求、模型输出、段落定位意见和报告；已有输出文件拒绝覆盖。审稿结果仍需人工核验。

## 逐章生成与故事记忆

- 在“章节阅读”选择章节，填写目标字数（100—10000）和本章要求，点击“逐场景生成本章”。长章按约1200字的场景拆分，章节独立生成候选；已有正文使用修订候选。
- 完成后可以在章节页查看候选并“采纳本章与记忆”。下一章基于已采纳章节继续。对话请求多章时，本轮仅交付最前面一章，明确提示剩余章节，不再等整批审稿后交付。
- 失败、取消或超时后，检查点保存在所属作品目录 `chapter-task.json`；章节页或记忆页可恢复。已完成场景不重复请求。重新生成会把旧检查点归档到 `task-history/`。
- “故事记忆”菜单展示按正文片段生成的摘要、事件、人物/物件状态、知情、故事线和伏笔。可以按章节、类型、关键词筛选，展开原文出处。摘要和记录是模型抽取结果，不是人工核实的世界事实。
- 已有作品点击“整理全部记忆”建立索引；新章节随采纳一起保存正文与记忆。不会把章纲自动作为已经发生的事实。旧章改稿会使依赖此前正文的后续记忆显示过期。
- 人物背景往事可按设定与章纲展开，不因“回忆、当年”等词阻断。引用已写事件时可注明实际来源章节，输入会带上对应原文；引用不存在、未来或空白章节时会显示实际可用来源及修改办法。
- 上下文按相关实体和明确章节引用选择，采用保守字符估算和固定预算；不是供应商精确tokenizer。场景预算仅作参考，允许不均分；完整初稿汇总后才按整章范围验收。超出范围时按各场景占比分担篇幅调整，达到整章范围立即停止调整。定向编辑携带实测字数和前后相邻场景，保留原稿、原始输出及较优修订；单场三次未达到参考范围会继续调整其他场景，整章仍越界才中断。输出触顶保留片段并有限续写。

当前边界：每次模型请求仍为非流式，按返回片段保存；网络在响应返回前断开时无法保存尚未收到的文字。首版没有自动连续写完100章的队列、完整事件图谱、人物知情权限引擎或全书语义一致性保证。未采纳章节不会被后续任务当作正式事实。大量既有章节首次建索引会耗时，可中断后恢复。

验证：`npm test`；桌面交互 `NODE_PATH=<含playwright的目录> node scripts/verify-memory.cjs`（独立临时作品与模拟模型，验证真实IPC）；真实模型隔离验证 `node scripts/evaluate-chapter.mjs`，中断后加输出目录和 `--resume`。验证脚本不修改正式作品。

### 带证据审稿与段落补丁

当前正文流程 `chapter-memory-2` 在篇幅调整完成后执行带出处的审稿。矛盾需两处可定位的陈述；“缺少前情”只能针对已提供的原文范围，不把检索未命中当成全书不存在。指代疑点及普通建议不触发强制改稿。

能够依据原文确定的矛盾，保留所引事实；缺少出处的断言可最小删除，不能临时补造对白或往事。无法裁决的关键事实保留为待确认错误与检查点，不自动选择。

修订只替换审稿指定段落，校验原文版本、位置和范围，其他段落原样保留。独立复核检查原问题、保留事实、无依据新增及相关后文；最多两轮修订，每轮最多两次补丁尝试。未通过的补丁不会写入当前草稿。审稿开始后不再为了篇幅重写整场。

检查点 `paragraphReview` 保存引用、补丁前后文字、复核及提交链；旧 `chapter-memory-1` 检查点先归档再迁移，已生成场景保留，旧审稿缓存失效；仍能匹配原文的旧问题必须逐项重新确认或驳回并给出出处，避免重审时漏项。新正文通过后才抽取候选记忆，采纳时同步保存正文与记忆。语义复核仍依赖模型，并不保证零误判。

### 规划入口 DAG

规划不完整时，正文请求先进入可恢复的规划图：意图与规模识别 → 基础规划 → 每批最多3章的章纲节点 → 待采纳候选。已有非空基础规划、角色和正文保留。章纲节点的输出schema不允许content；程序将新章节正文设为空，不能将“12章每章5000字”解释成一次输出6万字。

基础齐全而chapters为空也进入该图，不再回退旧的整份候选生成。每个节点在chapter-task.json的graphs中记录状态和结果；恢复跳过完成节点，失败批次通过原有结构校验后才提交。当前调度串行执行，DAG用于明确依赖和恢复边界，并不表示所有节点并行。

章纲候选采纳后进入现有逐章/逐场景正文流程；下一章依赖此前章节采纳。尚未提供无人值守的100章自动采纳队列，也未将审稿修订循环整体改写成纯DAG。

### 连续性问题处理

审稿提出“需要确认”时，先由独立裁决步骤核对原文和后文，能确定保留依据或安全删除无出处断言时自动修订，再执行补丁复核。无法裁决、自动修订次数用尽或补丁复核反复失败时进入 `awaiting_input`，不把正常的作者取舍当作错误通知。

确认放在创作对话中，一次只问一个问题。可以点选保留依据，也可以直接在聊天输入框回答；详细原文折叠展示。问答写入聊天记录，单题回答同时保存在检查点，全部答完才恢复模型修订；关闭应用后仍停在未答问题。其他页面只提供前往对话的提示。作品变化后拒绝旧选择。未通过审稿的正文不进入正式作品或正式记忆，最终仍需采纳候选。修订循环有次数限制，作者选择不等于跳过复核。

发送模型的审稿材料中，原文只保留一份，问题和作者决策使用可定位的引用地址。UI选项、来源哈希和历史快照留在本地，不重复塞进提示；来源内容不静默截断。
